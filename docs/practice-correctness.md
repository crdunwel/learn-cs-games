# Practice question correctness

This document covers the eight practice generators. The mock exam has its own validator and audit. Generated questions are fixed, bounded templates; they are not written by a language model at runtime.

## What is guaranteed, and what is not

`validatePracticeQuestion(gameId, question)` independently recomputes the expected answer and checks the displayed inputs, source structure, state transitions, and choice integrity. The game registry runs this guard before returning a question, including when a worksheet requests a question. A mismatch throws; it is not silently retried or shown to the student. The validator does not import any generator or its solution function. Tests deliberately corrupt answers, C source, stack states, and queue traces to check that they are rejected.

The correctness argument below applies to the current templates and stated input domains. Exhaustive finite checks, mathematical invariants, and compiled C checks support it. It is **not** a machine-checked formal verification of JavaScript, the browser, or the C compiler. Seed sampling alone is not a proof, and we do not treat it as one. The larger structural domains are covered by template arguments and an independent check of every actual generated instance, rather than by claiming that every possible infix expression or array value combination was enumerated.

Free-form student C is not executed or mechanically proven correct. A narrow malloc practice grammar grades one allocation assignment against explicit type/count/size metadata; native tests compile model/equivalent examples, never arbitrary student drafts. Written exam responses require comparison against a rubric. Practice C choices have one intended correct option under the stated assumptions.

## Template arguments

| Game              | Domain and correctness argument                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stack & Slay      | Numeric operands; binary `+ - * /`; balanced parentheses; 3–9 operands. Generation recursively combines valid expressions, so syntax stays valid. Within each parenthesis level, higher precedence binds first and equal precedence associates left. The generator uses an operator stack; the independent solver uses recursive grammar and postorder traversal. A second model keeps one pending sum and product per parenthesis frame and checks **every** intermediate stack and output state. Checkpoint A is the state after the indicated number of processed tokens, before the final flush. This is conversion of syntax, not numerical evaluation: an expression that would divide by zero is still a well-defined conversion exercise. |
| Poolside Queue    | Capacity 4–6; any valid front and occupancy 0…capacity; 1–3 operations. Invariant: occupied cells are the consecutive circular positions beginning at front, and `rear = (front + count - 1 + capacity) % capacity`. Enqueue when not full appends one FIFO item; dequeue when not empty removes the first. Failed operations preserve the whole state. The empty-state index convention is stated explicitly. An independent ordinary FIFO list reconstructs all physical cells and verifies every transition/result/index, including wraparound.                                                                                                                                                                                                |
| Big-O Afterglow   | The code asks for the tightest bound, with positive n, constant-time `work()`, and no arithmetic overflow. Exact call counts are `K`, `ceil(n/s)`, `n²`, `floor(log₂ n)`, `n floor(log₂ n)`, `n(n−1)/2`, and `2n` for the seven templates. These directly imply the stated tight classes: constant, linear, quadratic, logarithmic, n log n, quadratic, and linear. The native suite checks every K=3…20 and s=2…5 source variant. Scaling uses the **exact** model W(n)=nᵖ, p=0…3, factor=2…4, so W(fn)/W(n)=fᵖ; it does not infer an exact multiplier from Big-O alone.                                                                                                                                                                         |
| Recursion Reverie | Scalar domains are bounded: n≤18 for totals; decrement 1…4; base 0…4; a=2…9, b=0…4 for powers; recurrence n=0…7. For total, k=ceil(n/d) recursive additions form an arithmetic progression, giving `kn − dk(k−1)/2 + base`. Printing before recursion yields descending order; printing after it yields ascending order by induction from the empty n=0 output. Array recursion moves one index toward a checked bound; each element contributes its own value or a 0/1 even predicate. Power follows induction on nonnegative b; recurrence is checked against a bottom-up table. `countCalls` decreases by a positive d and stops at n≤0, including when it skips below zero. Values fit even a 16-bit signed int in these domains.             |
| Link & Bloom      | Lists have 3–5 nodes, with value i in 10i+1…10i+8. Insertion positions are 1-based and generated at 2…length+3; walking at most p−2 next pointers reaches the predecessor or the last node. Saving the old next pointer before changing it preserves all original nodes and order. Mutation visits each original node once: after inserting, the extra `front = tmp` skips the new node before the ordinary advance. Each matching original contributes exactly one new node. Pointer-order questions always have a following node, so severing that link is genuinely wrong. Recursive freeing reads next before freeing its owner. All shown allocations are assumed to succeed; inputs are finite acyclic lists.                               |
| Golden Search     | Length 5…10; first value 1…20; gap 2…8, so arrays are strictly increasing. Targets are existing items, one below the first, one above the last, or one above an item. The invariant is that any match still lies in the inclusive interval [low, high]. Comparing with mid excludes the impossible half and mid, strictly reducing a nonmatching interval. Empty intervals return −1. A recursive interval-partition oracle checks the iterative trace, and ordinary linear lookup independently checks the returned index. Every possible generated array/key pair is enumerated, including all reached intervals.                                                                                                                               |
| Memory Garden     | Counts 12…240 and explicitly supplied type sizes make requested bytes count×element size. `calloc` zero-initializes the integer elements. A C string of L bytes before its terminator requires L+1 bytes. Positive-size `realloc` failure preserves ownership of the old allocation; the question explicitly requires freeing it before clearing its pointer. Successful growth preserves old entries, and questions access only those entries. Nested ownership is strings → pointer array → Book; the inline title array is part of Book and must not be separately freed. Allocation-success assumptions and the unusual free-on-failure policy are stated in the questions.                                                                   |
| Basecamp          | Every value 0…4095 and every ordered pair of distinct bases in {2,8,10,16}. Interpreting digits by Horner's recurrence v←base×v+digit is independent of the generator's number-to-string operation. Both source and answer must evaluate to the same value, with every digit inside its base. All 49,152 combinations are enumerated, including zero.                                                                                                                                                                                                                                                                                                                                                                                             |

All choice lists must have at least two distinct entries and exactly one copy of the generated correct answer. Existing evaluation tests also check that the accepted-format rules do not make a distractor equivalent to the answer.

## Repeatable verification

Run `npm test`. A C11 compiler is required for the native test; set `CC` when needed. Missing compiler/tooling is a failure, not a silent skip. The native test creates and removes its own temporary files.

`tests/practice-validation.test.js` checks:

- Every base/value/direction combination: **49,152** cases.
- Every possible generated search array/key pair: **13,440** cases, each full trace and all four question categories.
- Every sum, power, recurrence, print, and countCalls scalar parameter combination. Array checks exhaust lengths, start/end/empty intervals, active positions, and element contributions (0…9 sums; 0…19 parity). Sum linearity and additive predicate counts extend these checks to combinations of multiple nonzero elements.
- Every circular state for capacities 1…6, every front/count, and all eight three-operation enqueue/dequeue sequences. Their prefixes also check shorter sequences. Values are arbitrary FIFO payloads; only ordering matters.
- Every binary expression tree through four operands, four operator choices, and optional parentheses at every internal node: **2,697** generated forms, including every intermediate state. Larger forms are checked individually at runtime and follow the same grammar/frame invariant.
- All allocation counts/type sizes/string lengths/reallocation factors/author counts/title sizes, all preserved-index/value classes, all insertion positions/values, and all list parity branch patterns.
- Deterministic regression seeds across every game and level, with intentionally corrupted answers/source/traces rejected. These supplement rather than replace the exhaustive and algebraic checks.

`tests/practice-native-c.test.js` compiles **438 actual displayed-source functions**, using C11, `-Wall -Wextra -Werror`, AddressSanitizer, and UndefinedBehaviorSanitizer. It executes:

- Every scalar recursion source variant and all allowed scalar arguments; array boundary/contribution checks; both print directions; completed base-case/recursive-step choices.
- All **27** loop source variants at every n=1…64, including nonpowers of two, compared with exact call counts (not an approximate growth-ratio threshold).
- All **273** insertion position/value source variants across valid list lengths; all six mutation variants and every parity pattern; safe pointer insertion and recursive freeing, including a NULL list.
- All **94** binary-search target-literal variants on every generated array (78,960 executions), with an independent linear lookup oracle.
- Actual generated calloc statements for all counts; type-size endpoints; every string length; successful resize preservation; nested cleanup for every author count. Failed realloc is injected deterministically to execute the exact failure branch, rather than hoping the allocator fails under memory pressure.

Function names are changed only to avoid collisions in the combined C file. Counting output/work, tracking the malloc size, and injecting realloc failure are explicit harness instrumentation; no JavaScript translation of C is used. Sanitizers check executed paths for memory and undefined-behavior errors, not arbitrary paths or a formal C semantics proof. Compiler acceptance and finite executions complement the template arguments above.

## Maintaining this guarantee

A new template must add a validator case, input-domain constraints, an independent answer derivation, boundary coverage, and native C coverage where C behavior is involved. Changing C semantics must update its explicit source contract and mathematical argument. Do not weaken the validator or retry around a mismatch to make a test or a generated question pass. Static lesson prose is reviewed separately; the runtime question guard does not claim to validate every explanatory English sentence.

## Additional Memory Garden domains

The six added templates have independently enumerated semantic domains in `tests/memory-variety.test.js`: true-array counts 12…240; every valid calloc index for those counts; alias initial value 1…40 × increment 1…9 × initialized index 0…2; pointer start 1…20 × offset 1…3 × valid index; shrink start 1…20 × retained length 1…5 × retained index; row count 1…8 × column count 2…10. Unused random metadata does not affect these answers.

For array length, cancelling the common positive element size yields the declared count. Integer calloc reads yield zero. Aliases share one address, so the write contributes exactly the increment to the initialized element. Pointer indexing is addition of the offset and relative index, with their sum bounded by 4. Successful shrinking preserves the selected prefix value; no discarded or uninitialized entry is read. Each successful row allocation adds one owned block, so cleanup requires rows+1 frees. Generated values remain in the range of even a 16-bit int. The runtime guard binds these arguments to the displayed C and independently recomputes each result. Mutation tests reject changed answers, source, bounds, and array diagrams. Native C assertions cover all six templates with boundary literals and all index/ownership branches; they supplement, rather than replace, the full finite-domain checks.

## Expanded domains and independent guards

Complexity, recursion and search now delegate to focused independent modules: [bigOValidation](../src/engine/bigOValidation.js), [recursionValidation](../src/engine/recursionValidation.js), [searchValidation](../src/engine/searchValidation.js). They preserve original finite/template checks and add cubic loops, binary/linear search complexity, independent inputs, concrete exact time/work scaling, Fibonacci, factorial permutation counts with restored swap state, recursive binary search, and five additional iterative search asks. Domain-specific arguments, exhaustive counts and native execution boundaries are in the owning [Big-O](games/bigO.md), [recursion](games/recursion.md) and [search](games/search.md) docs. Their new tests are automatic `npm test` entries.

Ordinary queues use a separate independent list transition guard alongside the circular guard. Short malloc contracts use [mallocValidation](../src/engine/mallocValidation.js), separate from the student-answer parser. New test suites include rejected corrupted questions, exact finite domains, parser false positives, sanitizer execution of actual displayed/model C, and once-only partial XP. These add coverage without replacing the earlier original-template native checks.
